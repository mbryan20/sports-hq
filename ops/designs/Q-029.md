# Q-029 (reopened) · The 8:02am kick skips when a GitHub cron committed in the 20 minutes before 8am

## Problem
Q-029's Measure ("every weekday a data commit 8:00-8:15am CT for two weeks", Nov 9-20) passed 8 of 10 weekdays.
Zero `workflow_dispatch` runs were cancelled (all laptop dispatches since Nov 9 succeeded). The two misses:
- Mon Nov 16: the laptop was silent overnight and its first kick came 8:27am CT (14:27Z). That is Q-037's problem
  (one push per outage, the 4am "no 2:55 kick" push), not this design's.
- Wed Nov 18: GitHub's `*/20 13-14 * * *` digest cron (the 13:40Z slot, run 356) committed `status.json` at 13:49:04Z
  = 7:49am CT, before the digest is due (`digest.due` needs 8:00). At 14:02Z the laptop's `Kick run` (8:02am CT,
  `kick.ps1 -FreshMinutes 20`) found data 13 minutes old and skipped (`ops/kick.ps1` lines 173-182). Nothing else ran
  until the 9:02 kick (15:02Z), so `digest:2026-11-18` went out at 9:02am CT, an hour late.
The freshness skip is meant to avoid starting a second loop beside a running one. Here no loop was running: the 13:49
commit was a one-pass cron run, and it came before the digest was due. In CST (since Nov 1) the 13:40Z cron slot is
7:40am CT, so this repeats whenever GitHub runs that slot 2-21 minutes late: Fri Nov 20 it committed at 13:39:08Z,
23 minutes before the kick, and only just missed the skip. Weekday status.json commits 13:40-14:01Z: 1 of 10 days
(Nov 18); 13:30-14:01Z: 2 of 10 (Nov 18, Nov 20).

## The change
`ops/kick.ps1`, the `-FreshMinutes` block only:
1. New switch `-DigestHour 8` (the 8:02 trigger passes it; the other hourly triggers can pass it too, it is harmless).
2. When the freshness check would skip, first read `docs/data/digest.json` on main
   (`gh api repos/<repo>/contents/docs/data/digest.json --jq .content`, base64 → `generated`). If local time is at or
   after `DigestHour`:00 CT and `generated` is not today at or after that hour (CT), the digest is due and nobody has
   built it: start `run.yml` anyway and log "started: digest due (data committed N min ago)".
3. Otherwise unchanged: skip as today. If the digest read fails, keep today's behaviour (skip) and log it, so a GitHub
   hiccup can't double-start loops.
`run.yml` needs no change: `run.digest_due` already reads origin/main's digest.json, so a kick that lands beside a
cron run that just built the digest won't push it twice.
Nothing new shows on the page or in pushes; the effect is that the 8am digest push is on time on days like Nov 18.

## How to test before shipping
- Dry run: add `-WhatIf`-style `-DryRun` (log the decision, don't dispatch) and run it on the laptop against today's
  repo state; the log line must say why it would start or skip.
- Replay the decision on the 10 weekdays Nov 9-20 from git history (status.json's last commit before 14:02Z and
  digest.json's `generated` at that moment): the new rule must start on Nov 18, and must give the same answer as today
  on the other 9 days (it starts on 8 of them; Nov 16 had no kick). A short Python helper over `git log` is enough;
  it lives in the build session, not in the repo.
- Measure after shipping: two more weeks with a data commit and the digest 8:00-8:15am CT on every weekday the laptop
  kicked at 8:02 (the kick log `.cache/sports-hq-kick.log` shows "started: digest due" on any day the old rule would
  have skipped). No health.json check moves (`status.json` / `digest:` keys in `state/alerts.json` are the evidence).

## Risks and roll back
Low. Worst case two runs at once (a cron run committing at 7:59 and still looping is the only way): both are allowed
today already (a dispatched run that finds another going 10+ min does one pass) and `digest_due` stops a second push.
Roll back = drop `-DigestHour` from the `Kick run` task (Michael's PowerShell, `ops/designs/Q-014.md` commands) or
revert the block. The scheduled-task change needs Michael's own PowerShell window (re-register `Kick run` with the
new argument); a Claude session must not touch the token.
