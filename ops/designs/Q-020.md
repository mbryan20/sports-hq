# Q-020 · Laptop jobs that fail say so

Drafted by the nightly improvement pass, 2026-11-04. Nothing here is built until the item's Decision says approved.

## Problem
The monthly review (`reviews/2026-11.md`, Freshness) found 4 of 17 laptop daily syncs did nothing (Chrome extension not
connected Oct 25 and Oct 30; signed out of the built-in browser Oct 26 and Oct 28) yet show "succeeded" in the task list.
The site only learns about it indirectly: `shq/run.py` `job_health` reads each job's last *delivery* (`captured` in
`state/kosmonauts_roster.json`, the ESPN snapshots, `cards.json`), and `docs/lib/core.js` `footHTML` greys a job out after
30 hours. A failed 7:30am sync looks fine until the next afternoon, and the reason is never shown.
The claude-audit plan (`plan.md` Phase 3 #3) already covers the task-prompt half ("report FAILED and push an alert when
nothing synced"). This design is the Sports HQ half, so the two land together.

## The change
1. New `state/laptop_runs.json`: one entry per job, `{job, at, result: "ok" | "failed", reason}` (latest run only, plus the
   last failure). Written by a new `py -m shq.laptop_run <job> ok|failed "<reason>"` that also commits and pushes that file
   (merge, never rebase), so a failed run, which commits nothing else, still reaches the site.
2. Each laptop task prompt ends with that command: ok after its data is committed, failed with the reason otherwise, and
   then prints `FAILED: <reason>` as its last line. The daily sync, the 5 picks tasks, the guillotine bid check and the
   safety net. Prompt edits go through the claude-audit batch approval (scheduled tasks are its area); copies go into
   `ops/tasks/` (the daily sync has none yet).
3. `shq/run.py` `job_health`: add `attempt`, `result` and `reason` from `laptop_runs.json` next to today's `last` delivery.
4. `core.js` `footHTML`: a job whose latest attempt failed shows red with the reason ("Kosmonauts roster: failed 7:30a,
   Chrome not connected"), not just grey after 30 hours (dashboard redesign session owns `docs/lib/`).
5. `shq/run.py`: `push_once("laptop-failed:<job>:<at>", ...)` once per failure, so a failed morning sync is pushed on the
   next cloud pass instead of the `roster-stale` alert many hours later.

## Test before shipping
- `tests/test_laptop_run.py`: ok and failed entries round-trip; `job_health` merges them; a failure pushes once.
- Dry run on the laptop with Chrome closed: the sync must end with `FAILED: Chrome not connected`, the footer must show the
  failure after the next cloud pass, and one push must arrive.
- Then 2 weeks of normal runs: zero "succeeded" runs that delivered nothing (compare the task run list with the commits,
  as the monthly review did). No health.json check exists for this; the monthly review re-counts it.

## Risks and rollback
- A laptop commit racing the cloud's data commits: the file is touched only by the laptop, and the commit uses
  `git pull --no-rebase --no-edit` with retries, like `picks/pp/publish.py`.
- False alarms on a task that legitimately skips (e.g. roster fresh within 20 hours, `save_roster.py:72`): treat "skipped,
  fresh" as ok.
- Rollback: revert the commit and remove the last line from the prompts; the old `last`-based footer still works.
