# Q-074 · A cron run that starts within 10 minutes of a loop becomes a second loop (and pushes twice)

## Problem
Mon Nov 23 (Monday night football window), two `run.yml` loops ran side by side for 2.5 hours:
- Run 447 (laptop dispatch, 19:02:06Z) looped until its time limit and handed off at 00:37Z.
- Run 449 (the handoff, `github-actions[bot]`, created 00:37:13Z) looped 00:37Z-03:07:11Z, as designed.
- Run 450 (scheduled, created 00:38:26Z, 73 seconds later) also looped, 00:38Z-03:07:14Z.
Result: 16 pairs of data commits one to seven seconds apart (00:37Z-03:07Z, e.g. `0f52c1d` 03:07:07Z and `002730d`
03:07:09Z), twice the ESPN / Sleeper reads, and one duplicate phone push: both loops wrote the same key
`espn:nba:184031:w6:espn4066259:fa` to `state/alerts.json` (commit `f0cb0f0` at 01:37:09Z, then `d8f1154` at
01:37:10Z re-stamping it). Q-049 (one push per piece of news) assumes one pass at a time.

Cause (`.github/workflows/run.yml`, Run step): a run does one pass only when another in-progress run is older than
600 seconds (`createdAt < now - 600`). Run 450 saw run 449, 73 s old, and treated it as a one-pass run. So any
non-handoff run that starts in the first 10 minutes of another loop also loops. Scheduled runs and laptop kicks are in
different concurrency groups by design (Q-014/Q-029), so GitHub does not queue one behind the other.

## The change
`.github/workflows/run.yml`, Run step only. Keep today's check at the start, and add a second one after each pass:
1. After `commit_data.sh`, before `python -m shq.run --keep-watching`, list in-progress `run.yml` runs again
   (same `gh run list` call). If another in-progress run has a lower `databaseId` (started earlier) and was created
   more than 120 s before this one, stop looping: log "older run is looping: stopping after this pass".
   Oldest run wins; the newer one ends after its first pass, so the overlap is one pass (about a minute), not hours.
2. Handoff runs keep their exemption on the first pass only (the loop that started them is still finishing its last
   seconds); from the second pass on they use the same rule. Because the old loop has ended by then, the handoff keeps
   looping, and a cron that started just after the handoff (run 450's case) stops.
3. If the `gh run list` call fails, keep looping (today's behaviour) and log it, so a GitHub hiccup can't stop the watch.
Nothing changes on the page or in pushes, except that the duplicate push and the doubled data commits go away.
Optional second guard (separate, only if the first proves not enough): before sending a keyed push, `shq.notify`
re-reads `state/alerts.json` from origin/main and skips a key stamped in the last 5 minutes.

## How to test before shipping
- Replay from the run list: for the last two weeks of `run.yml` runs (GitHub connector: number, event, created,
  updated), mark every pair of runs that overlapped by more than 15 minutes. The new rule must end the newer one after
  one pass in every pair (Nov 23-24: 449 keeps looping, 450 stops), and must never stop the only looping run (in
  particular never a handoff while its predecessor has already ended).
- Workflow test: a `dry_run` dispatch with `loop_minutes: 15`, then a second `dry_run` dispatch 2 minutes later: the
  second must log "older run is looping" after its first pass and end; the first must keep going.
- After shipping, over the next two NFL Sundays/Mondays: zero minutes with two `data:` commits within 15 s of each
  other, and no `state/alerts.json` key re-stamped within a minute by a second commit. No health.json check moves.

## Risks and roll back
Low-Med: a wrong rule could end the only loop and leave the injury watch idle mid-game. The 120 s margin and
"oldest wins" keep at least one loop; the `gh` failure path keeps looping. Roll back = revert the added block
(one commit; the start-of-run check is unchanged).
