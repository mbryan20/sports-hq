# Q-014 · Morning runs that don't wait on GitHub's late crons

Drafted by the nightly improvement pass, 2026-11-05. **Decision: approved 2026-11-05** (Michael, "Yes, build all", via Claude Ops;
built as R1 / Q-029). What was built differs from the draft in a few places: see "As built" at the end.

## Problem
`run.yml` asks for a run every hour (`7 * * * *`) plus every 20 min at 8am CT, but GitHub drops or delays most of them.
- Wed Nov 4: no run between 2:59am and 11:06am CT (data commits 08:59Z, then 17:06Z: an 8h07m gap), so the 8am digest
  landed about 3 hours late. Nov 3 00:00Z - Nov 5 10:00Z: 17 runs started (2 more cancelled) in 58 hours, although the
  hourly slot alone asks for 58.
- October (`reviews/2026-11.md`, Reliability): 26 runs "cancelled" before starting, 7 manual dispatches dropped (Oct 25,
  28, 30), no run 8am - 1pm CT on 3 of 8 weekday mornings (Mon Oct 26: 6h22m gap).
- Why dispatches vanish: `concurrency: group: sports-hq-run, cancel-in-progress: false` keeps one running and one waiting
  run; a newer queued run replaces the waiting one, so a "force" press made while a game-day loop is running is
  silently replaced by the next cron.
- Same pattern for the health job: `model-health.yml`'s 2:50am CT slot ran at 10:37am, its 4:50am slot at 12:15pm (Nov 4).

## The change
1. **Laptop kick at 7:35am CT.** The 7:30am laptop daily sync already runs on time every day. Its last step becomes
   `gh workflow run run.yml` (after its roster commit, whether the sync succeeded or not), so the 8am digest is built
   from a run that starts on time and uses the fresh roster. `shq/run.py`'s `digest.due` decides whether to push; no flag.
   The prompt edit is a claude-audit batch item (scheduled tasks are that area); a copy of the prompt goes into
   `ops/tasks/daily-sync.md` (none exists yet; see Q-021).
2. **Tuesday Weekly:** the 7am Weekly (`weekly_due`) then builds on the 7:35am kicked run at the latest, instead of
   whenever GitHub's next cron fires.
3. **Dispatches never dropped:** `run.yml` concurrency group becomes
   `sports-hq-run-${{ github.event_name == 'workflow_dispatch' && github.run_id || 'cron' }}`, so each dispatch gets its
   own group and runs at once. A dispatched run does one pass and stops (no 10-minute loop: wrap the `while` in
   `[ "${{ github.event_name }}" = workflow_dispatch ] && break` after the first commit), so it can't run alongside a
   game-day loop for hours.
4. **No double digest:** before the digest push, `run.py` re-reads `docs/data/digest.json` from `origin/main`
   (`git fetch` + `git show`) and skips if another run generated it in the last 30 minutes; the push becomes
   `push_once(f"digest:{date}")` so `state/alerts.json` also guards it.
5. Same kick for the health job: the nightly pass (this task) already dispatches `model-health.yml` when health.json is
   over 20 hours old; no change.

## Test before shipping
- Unit: `tests/test_digest.py` gets a case where digest.json was generated 10 minutes ago on origin: no second digest push.
- Dry run: dispatch `run.yml` with `dry_run` while a scheduled run is in progress: both must finish, neither cancelled.
- Two weeks live: every weekday has a data commit between 7:35 and 8:30am CT (Tue Nov 3's first run was 8:38am, a manual dispatch; Wed Nov 4's was 11:06am);
  zero `workflow_dispatch` runs with conclusion `cancelled` (`gh run list --workflow run.yml --event workflow_dispatch`).
  No health.json check covers this; the next monthly review recounts it (optionally add an `ops.morning_run` check).

## Risks and rollback
- Two passes at once (a dispatch beside a game-day loop) could both push the same swap alert in the same minute:
  `push_once` keys are committed state, so a race is possible but needs both runs inside the same ~1-minute pass. Low.
- If the laptop is off, nothing changes from today (crons still fire when GitHub runs them).
- Rollback: revert `run.yml` and the `run.py` digest guard; remove the last line of the sync prompt.

## As built (2026-11-05, Q-029)
- **Laptop kick = Windows Task Scheduler, not the Claude sync prompt** (the approved proposal's R1: "Windows scheduled job
  runs `gh workflow run`; no Claude usage"). `ops/kick.ps1` runs `gh workflow run` with the laptop's GitHub sign-in and logs
  every attempt to `%LOCALAPPDATA%\sports-hq-kick.log`.
  - `\SportsHQ\Kick run`: daily 7:02am CT, then every hour until 11:02pm. Starts `run.yml` unless `docs/data/status.json` was
    committed in the last 20 minutes (a run is already looping; it passes every 10 min). 7:02 builds Tuesday's Weekly (7am
    anchor); 8:02 builds the 8am digest (`digest.due` needs 8:00 or later), from the 7:30am sync's fresh snapshot.
  - `\SportsHQ\Kick model health`: daily 2:55am CT, starts `model-health.yml` (its crons ran 7-8 hours late).
  - Both: user level (Michael's account, runs while he's signed in; no admin, no password stored), "run as soon as possible
    after a missed start", 5-minute limit, a hidden console (`conhost.exe --headless`).
- **Dispatches never dropped:** `run.yml`'s concurrency group is `sports-hq-run-<run id>` for a dispatch and
  `sports-hq-run-cron` for scheduled runs. Instead of "a dispatch always does one pass", any run that finds another
  Sports HQ run going for 10+ minutes (a loop; a one-pass run ends in ~5) does one pass and stops; otherwise it loops like
  a cron run. So a laptop kick on a game night with no cron running still carries the injury watch.
- **No double digest:** `run.digest_due` builds the digest only if neither this checkout nor `origin/main` (fresh `git fetch`)
  already has today's; the push is `push_once("digest:<date>")` (a forced digest still pushes).

### The exact tasks (PowerShell, as Michael's user; no admin). Not created yet (Nov 5): the build session's permission check refused it
```
$kick = 'C:\Claude\sports-hq\ops\kick.ps1'
$set = New-ScheduledTaskSettingsSet -StartWhenAvailable -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -ExecutionTimeLimit (New-TimeSpan -Minutes 5)
$run = New-ScheduledTaskAction -Execute 'conhost.exe' -Argument "--headless powershell.exe -NoProfile -ExecutionPolicy Bypass -File `"$kick`" -Workflow run.yml -FreshMinutes 20"
$t = New-ScheduledTaskTrigger -Daily -At 7:02am
$t.Repetition = (New-ScheduledTaskTrigger -Once -At 7:02am -RepetitionInterval (New-TimeSpan -Hours 1) -RepetitionDuration (New-TimeSpan -Hours 16 -Minutes 1)).Repetition
Register-ScheduledTask -TaskPath '\SportsHQ\' -TaskName 'Kick run' -Action $run -Trigger $t -Settings $set -Description 'Sports HQ: start run.yml on time (Q-014/Q-029)'
$health = New-ScheduledTaskAction -Execute 'conhost.exe' -Argument "--headless powershell.exe -NoProfile -ExecutionPolicy Bypass -File `"$kick`" -Workflow model-health.yml"
Register-ScheduledTask -TaskPath '\SportsHQ\' -TaskName 'Kick model health' -Action $health -Trigger (New-ScheduledTaskTrigger -Daily -At 2:55am) -Settings $set -Description 'Sports HQ: start model-health.yml on time (Q-014/Q-029)'
```
The script runs from the main checkout (`C:\Claude\sports-hq`), so it follows whatever `ops/kick.ps1` is on main after the
next `git pull`.

### How to remove them
```
Unregister-ScheduledTask -TaskPath '\SportsHQ\' -TaskName 'Kick run' -Confirm:$false
Unregister-ScheduledTask -TaskPath '\SportsHQ\' -TaskName 'Kick model health' -Confirm:$false
```
(or Task Scheduler → Task Scheduler Library → SportsHQ → right-click each → Delete). Removing them only returns to GitHub's
own crons; nothing else depends on them. Check what they did: `Get-Content $env:LOCALAPPDATA\sports-hq-kick.log -Tail 20`.
