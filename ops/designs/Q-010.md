# Q-010 · Automatic $ per win-point assumes every future crop looks like this week's

Drafted by the nightly improvement pass, 2026-11-10. Nothing here is built until the item's Decision says approved.

## Problem
Every bid value is (win odds a player adds) × ($ per point of win odds). `warroom/model.js` `autoDpp` (lines 191-198)
sets that rate from this week's freed players only: it sorts them by win odds per $ (at the price that wins about 80%),
assumes the same crop at every waiver run I'm expected to see (`runs` = my expected weeks left), and takes the rate
of the deal where my FAAB would run out.

Two things are wrong with "the same crop every week":
- Crops differ a lot. Top winning bid per run, weeks 1-8: $150, $156, $80, $65, $57, $103, $56, $57
  (health.json `recs.details.winners_paid`).
- They shrink as the league's money drains. The six biggest winning bids per run added up to $342, $310, $301, $248,
  $154, $223, $167, $174. Late crops cost about half what early ones did, so pricing every future run like today's
  overstates what later players will cost early in the season.
And between waiver runs there are no freed players, so the rate is empty: tonight's bids.json has
`dollars_per_win_point: null`, and a "projected" freed row gets its value from that one team's roster alone.

## The change
Build the rate from the crops I'm actually likely to see.
1. `autoDpp(rows)`: the deal list becomes this week's freed rows (weight 1) plus, for each later waiver run, each
   rival's best players weighted by (chance that rival is cut that week) × (chance I'm still alive), both already in
   `BASE.sim` (`pCut`, `pAlive`). Walk down the list by win odds per $ until the weighted cost reaches my spendable
   FAAB; the rate is that deal's $ per point, as today.
2. A future player's two numbers, cheaply (a full `gains()` simulation per rival player is too slow for the page):
   - win odds added: from my lineup gain over the remaining weeks (`gR`, no simulation), converted with the line
     fitted through this build's simulated rows (dWin against gR); fall back to the last build's line if under 5 rows.
   - price: `priceFor(.8, rawEstimate(threats(s)))` with the cut rival removed and every rival's FAAB as it stands,
     so the draining money shows up in the price by itself.
   At most 6 players per rival and 4 runs ahead (the weeks `NEAR` already uses).
3. `bids.json` `budget`: `dollars_per_win_point` is now filled between runs too; new `dpp_basis`, e.g. "this week's
   6 freed + 31 likely-freed players over 4.6 expected runs". The page's $ per point slider (`S.dpp`) still overrides.
What changes for me: values (and so bids) stop jumping with one week's crop, and planning rows have a value before
the cut is confirmed.

## Test before shipping (out of sample)
Same replay harness as Q-025 (`export.js --replay` over `model.py` `calibration_cases`, the league as it stood at each
of the 8 past waiver runs; runs in GitHub Actions because Node isn't on the laptop):
- Stability: the rate at each run, old vs new. The new one's week-to-week swings (spread of the log rate) should be
  at least 25% smaller.
- Pace: follow each version's bids through runs 1-8 from $200, deciding wins against the real winning bids. Ship if
  the new version buys at least as much total win odds and isn't out of money before the run where the old one is.
- Forecast check: the cost of the next run's top six as predicted one run earlier vs what they went for (the
  $342 → $174 slide); the new version's miss should be smaller than "same as this week".
- health.json: add `rec.dpp` (info) so the rate is tracked nightly; `rec.would_win` and `rec.win_brier` are watched,
  not gated (5 bids on record).

## Risks and rollback
- Med: it moves every value. The fitted line is rough when few rows are simulated; the rate is clamped to between half
  and double the old method's until the replay says otherwise.
- Build time: `threats()` for up to 9 rivals × 6 players; no extra simulations.
- Rollback: revert the commit to `model.js`; `S.dpp` can pin the rate by hand meanwhile.
