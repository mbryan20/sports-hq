# Q-064 · Score the rival-by-rival win chances every night, time-forward

Drafted by the nightly improvement pass, 2026-11-13. Nothing here is built until the item's Decision says approved.

## Problem
Since the War Room revamp (Q-062, 4fef2c7, Nov 12) every claim's win chance comes from `model.js` `rivalWin` (each
rival's claim chance x the chance his bid beats ours), fitted by `build.py` `rival_model` each build. The old ladder is
only a fallback. But `shq/health.py` still scores the ladder only (`ladder_backtest`, checks `wr.price_est_mae`,
`wr.ladder_cov50` 0.56, `wr.ladder_cov80` 0.81, n=212, both ok), while Q-062's one-off replay showed that same ladder's
10-30% chances won 1 in 79 in weeks 6-9. The new model's 20% bids won 17-26% in that replay, and it ran cautious in the
middle (60% said, ~70% won). Nobody re-runs that as claims arrive. `rec.win_brier` (0.17, n=9, watch) scores only the
2-5 bids we recommend a week.

## The change
1. `warroom/export.js`: a `--rival-chances <file>` mode. Input: a list of {case D, rival_model fitted on earlier runs,
   targets}. For each target it runs model.js's own `rivalInputs` + `winChance(b, est, r)` and returns the bids that
   win 25%, 50% and 80% (`priceFor`), plus the stated chance at $0 and at the price actually paid. Same code as the page,
   so health can't drift from what Michael sees.
2. `shq/health.py`: `rival_backtest(cases, inputs, hist, me)`. For each waiver run from the 3rd on, fit
   `warroom.build.rival_model` on the runs before it only (time-forward, as the replay did), get the prices from step 1,
   and judge each target the way `rec_outcomes` judges a bid: wins only if above the top rival bid (ties lose; $0 wins
   only when nobody claimed). Michael's own claims are left out of the fit, as now.
3. New checks in section `warroom`: `wr.rival_cov25`, `wr.rival_cov50`, `wr.rival_cov80` ("Bids at the rival model's
   N% price that won", kind "target", tolerances 0.12/0.15/0.12 like the ladder's), `wr.rival_brier` (Brier of the
   stated chance at the price paid + $1, lower is better). `details.rival.by` splits by position, rank tier and legs
   early/late, like `prices.by`. Notes say which model the page uses (`price_model` from bids.json).
4. The three ladder checks become info (the ladder is a fallback); `wr.price_est_mae` stays as the raw estimate's miss.
5. Baselines: none set by the build. After the first run Michael OKs the baselines (the pass never edits
   `state/health_baselines.json`).
What Michael sees: nothing changes on the War Room page, bids.json or pushes; health.json (and Q-013's scorecard, when
built) says whether "Bid 50%+" really wins half.

## Test before shipping
- Weeks 2-9 history (212 claims, the cases `warroom_prices` already builds): the time-forward numbers must reproduce
  Q-062's replay within noise (20% bucket won 17-26%; 50% and 80% prices near 0.5 and 0.8 overall). If they don't,
  the replay or this check is wrong: find out which before shipping.
- Same run, old ladder time-forward on the same claims: its 10-30% bucket should again win about 1 in 79 (sanity check).
- `tests/test_health.py`: a fixture of 3 fake runs where rival A always bids 50% of his FAAB: the check says the 50%
  price wins about half; the fit never sees the run it judges; ties lose.
- Runtime: one Node call for all runs (the build already does one `--calibrate` call); health job stays under 25 min.

## Risks and rollback
- Small samples per split (RB n=40): show splits under 12 claims as info, as `prices.by` does.
- Week 10's run (Wed Nov 18) is the first with the new model live; before that every scored claim is a replay.
- Rollback: `git revert` the commit; the section's old ladder checks return to non-info.
