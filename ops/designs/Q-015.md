# Q-015 · Push log and "Recent alerts"

Drafted by the nightly improvement pass, 2026-11-04. Nothing here is built until the item's Decision says approved.

## Problem
Nobody can check which alerts actually went out. `shq/notify.py` `push_once` keeps only alert keys in `state/alerts.json`,
pruned after 21 days (`notify.py:36`), and plain `push()` (the 8am digest, "lineup fixed", "Week N plan ready": `shq/run.py`
lines 120, 308, 321) leaves no record at all. The monthly review (`reviews/2026-11.md`, Usefulness) could not say which
injured starters were caught before lock in October. Picks pushes (`picks/pp/publish.py:32`) and the laptop task pushes
(`ops/tasks/guillotine-bid-check.md`, `guillotine-safety-net.md`, `monthly-review.md`) are also unlogged.

## The change
1. `shq/notify.py` `push()`: after a successful send, append `{at, title, message, priority, tags, click, source: "cloud"}`
   to `state/pushes.json` and drop entries older than 60 days. Never write `topic` (the body dict is built separately;
   the log entry is built from the arguments only). Dry runs log nothing. `push_once` goes through `push`, so it is covered.
2. Laptop pushes write their own file, `state/pushes_laptop.json`, so a laptop commit can't conflict with the cloud's
   frequent data commits: a small `log_push(title, message, source)` in `shq/notify.py`, called from
   `picks/pp/publish.py` after its post, and a one-line `py -m shq.notify --log "<title>" "<message>" --source <task>` added
   to the three `ops/tasks/*.md` prompts after their `Invoke-RestMethod` (those prompt edits go through the claude-audit
   batch approval, since they change scheduled tasks).
3. `shq/run.py` puts the last 7 days from both files into `status.json` as `recent_pushes` (time, title, first 120
   characters). `docs/lib/core.js` `footHTML` gets a "Recent alerts (N)" line that opens the list in the drawer
   (the dashboard redesign session owns `docs/lib/`).
4. Workflow failure pushes (`curl` in run.yml, test.yml, war-room-v2.yml, picks-backup.yml) stay unlogged: they already
   show in the Actions history.

What Michael sees: a "Recent alerts" list on every layout's footer; nothing else changes and no push is added.

## Test before shipping
- `tests/test_notify.py`: a push writes one entry; the topic string never appears in either file; entries older than 60
  days are pruned; DRY_RUN writes nothing; `push_once` twice logs once.
- Run one cloud pass with a test push (`TEST_PUSH=1` dispatch) and check `state/pushes.json` and `status.json`.
- After one week: every key added to `state/alerts.json` that week has a matching entry in `state/pushes.json`
  (one-off check; then this is how the monthly review answers "did we catch it before lock?").
No health.json check moves; this item is about being able to audit, not model accuracy.

## Risks and rollback
- The repo is public: messages already appear on the public site (player and league names), so nothing new leaks, but the
  test must prove the topic never lands in the file.
- File growth: about 10-30 pushes a day × 60 days is well under 1 MB.
- Rollback: revert the commit; delete the two files.
